## 4.1 The VPC model

N: Look at the picture from the outside in. The outer dashed box is one V-P-C network, and it is global. It spans every region. = table | Auto mode or custom mode | Custom is the production answer
Fact | Consequence
**Auto mode** | One `/20` subnet per region, from `10.128.0.0/9`. Convenient, but overlaps every other auto-mode VPC
**Custom mode** | No subnets until you define them. **The production answer**

N: A V-P-C runs in one of two modes. Auto mode creates one slash twenty subnet per region, from the same range, ten dot one two eight. It is convenient, but it overlaps with every other auto-mode V-P-C, so two of them can never be peered. Custom mode creates no subnets, and you define them. That is the production answer. Auto can convert to custom, but never back. The default network in a new project is an auto-mode V-P-C, with permissive firewall rules. Production work starts on a custom-mode V-P-C, and the skip default network creation policy stops the default network appearing at all.

## 4.2 Subnets and IP ranges

= list | Subnets | Primary range, secondary ranges, reserved addresses
- One **primary IPv4 range**, plus optional **secondary ranges**, used by GKE for Pods and Services
- ==**Four addresses in every primary range are reserved**==: network, gateway, second-to-last, broadcast
- Ranges in one VPC, and across peered VPCs, **must not overlap**
- Subnets can be **dual-stack** or IPv6-only (*recognise*)
N: A subnet has one primary IPv4 range, and optional secondary ranges, which G-K-E uses for Pod and Service addresses. Four addresses in every primary range are reserved: the network address, the default gateway, the second to last, and the broadcast. So a slash twenty-nine has eight addresses, of which four are usable. Subnet ranges in one V-P-C, and across peered V-P-Cs, must not overlap.

= cmd | Resizing | Expand only, never shrink
Task | Command
Grow a full subnet | gcloud compute networks subnets expand-ip-range web-euc2 --region=R --prefix-length=19
> A subnet's primary range can be **expanded, without downtime, but never shrunk**.
N: A subnet's primary range can be expanded, to a shorter prefix, without downtime, as long as the larger range does not overlap anything. It can never be shrunk. So the subnet is out of addresses means expand I-P range. We made it too big has no fix, except a new subnet and a migration. Auto-mode subnets can grow up to slash sixteen.

= panel trap | Out of addresses | Adding a subnet versus expanding one
More addresses *in the same region for the same workloads*: **expand**.
A **new region**, or a separate range for a different tier: **create a new subnet** in the existing VPC.
A new VPC is almost never the answer to *"out of IPs"*.
N: Be careful here. More addresses, in the same region, for the same workloads: expand. A new region, or a separate range for a different tier: create a new subnet in the existing V-P-C. And creating a new V-P-C is almost never the answer to out of I-Ps.

= dia | Secondary ranges | How a VPC-native GKE cluster takes its addresses
p4-gke-ranges
N: Secondary ranges, and how a V-P-C native G-K-E cluster uses them. A subnet has one primary range, which gives the nodes their addresses. Pods take their addresses from one secondary range, a slash twenty-four per node at the default of one hundred and ten Pods. Services take ClusterIPs from another. A subnet can hold up to one hundred and seventy secondary ranges, and that limit cannot be raised. When the first Pod range runs out, you add another secondary range, here pods two, and give it to the cluster as an additional Pod range. Existing node pools keep their range, and new node pools take addresses from the new one. Autopilot from version one point twenty-six, and Standard, both support it. No new cluster.
V: Pod range full: add a secondary range, and a new node pool. Not a new cluster.

## 4.3 Routes

= table | The routing table | Four kinds of route
Route type | Created by | Notes
**Subnet routes** | Automatically, per range | Cannot be deleted; make every subnet reachable across the VPC
**Default route** `0.0.0.0/0` | Automatically | Priority 1000; delete it to cut internet egress paths
**Custom static** | You | Destination, next hop, priority, optional **network tags**
**Dynamic** | **Cloud Router**, via BGP | Learned over VPN or Interconnect; regional or global per routing mode
N: Every packet leaving a V-M is matched against the V-P-C's routing table. Four kinds of route. Subnet routes are automatic, they cannot be deleted, and they make every subnet reachable across the V-P-C. The default route goes to the default internet gateway, at priority one thousand. Delete it, and you cut all internet egress paths. Custom static routes are yours, with a destination, a next hop, a priority, and optional network tags so that only some V-Ms use them. And dynamic routes are learned by Cloud Router, through B-G-P, over V-P-N or Interconnect.

= table | Route selection | Most specific prefix first, then priority
Step | Rule
1 | The **most specific prefix** wins
2 | Among equal prefixes, the **lowest priority number** wins
3 | Equal priority spreads traffic (ECMP)
Note | Subnet routes cannot be overridden by a less specific custom route
> Next hops: a VM, an internal IP, an **internal passthrough Network LB**, a Classic VPN tunnel, the default gateway.
N: How is a route chosen? The most specific prefix wins. Among equal prefixes, the lowest priority number wins. Equal priority spreads traffic across routes. And subnet routes cannot be overridden by a less specific custom route. The next hop of a custom static route can be a V-M, such as a firewall appliance, an internal I-P, an internal passthrough load balancer for highly available appliances, a Classic V-P-N tunnel, or the default internet gateway.

= panel new | Custom static routes | The guide now names them
Usual stems: send a range through a **network virtual appliance**; route only **tagged** VMs through it; give tagged VMs a **higher-priority** path.
`gcloud compute routes create to-onprem --network=vpc-prod --destination-range=172.16.0.0/12 --next-hop-instance=fw-1 --tags=needs-inspection --priority=800`
==A route only forwards.== The appliance VM also needs **IP forwarding** (`--can-ip-forward` at creation), and firewall rules still apply.
N: The guide now names custom static routes. The usual stems: send traffic for a range through a network virtual appliance, route only tagged V-Ms through it, or give V-Ms with a special tag a higher priority path. The command on screen does all of that, with next hop instance, tags and priority. And remember that a route only forwards. The appliance V-M also needs I-P forwarding enabled, with dash dash can I-P forward at creation, and firewall rules still apply.

= dia | Dynamic routing mode | Regional or global decides who can use learned routes
p4-routing-mode
N: Every V-P-C has one dynamic routing mode, and it decides which regions can use the routes a Cloud Router learns over B-G-P. On the left, regional, the default. The Cloud Router in europe-west4 learns the on-premises range, and programs it only in europe-west4. V-Ms in us-central1, on the same network, have no route, and cannot reach on-premises. On the right, global. The same router's routes are programmed in every region, so us-central1 reaches on-premises through the same tunnels, with an inter-region cost added to the route's priority, so a closer connection wins where one exists. Global mode also makes the router advertise every subnet of the V-P-C to on-premises, not just its own region's.
V: Reachable from the V-P-N's region, but not from another region of the same V-P-C. That is the routing mode.

## 4.4 Firewall rules and Cloud NGFW policies

= table | VPC firewall rules | Distributed, stateful, and lowest number wins
Component | Values
Direction | **Ingress** or **egress**
Action | Allow or deny
**Priority** | **0–65535, lower wins**; default **1000**. Ties: deny beats allow
Targets | All instances · **network tags** · **service accounts**
Source or destination | IP ranges; for ingress also source tags or source service accounts
Protocols, ports, logging | `tcp:443`, `udp:53`, `icmp`; logging off by default, per rule
N: Firewalls are distributed and stateful. They are enforced at each V-M's network interface, and return traffic of an allowed connection is allowed automatically. Google's firewall product is now called Cloud Next Generation Firewall, or N-G-F-W, and it has two kinds of rule containers. First, the classic V-P-C firewall rules. Each rule has a direction, an action, and a priority from zero to sixty-five thousand five hundred and thirty-five, where lower wins, and the default is one thousand. On a tie, deny beats allow. Targets can be all instances, network tags or service accounts. Sources can be I-P ranges, and for ingress also tags or service accounts.

= tiles | Implied rules | Present in every VPC, and invisible in the list
allow | all egress, at priority 65535
deny | all ingress, at priority 65535
always | the metadata server `169.254.169.254` is reachable
blocked | egress to TCP port 25 on external addresses
N: Two implied rules exist in every V-P-C, invisible in the list: allow all egress, and deny all ingress, both at the lowest priority. Some traffic is outside the firewall's control altogether. The metadata server is always reachable. And egress to T-C-P port twenty-five on external addresses is always blocked, so you cannot send email directly from a V-M.

= cmd sm | Firewall commands | Allow HTTPS, allow health checks, log a rule
Task | Command
HTTPS from anywhere to VMs tagged `web` | gcloud compute firewall-rules create allow-web --network=vpc-prod --direction=INGRESS --action=ALLOW --rules=tcp:443 --source-ranges=0.0.0.0/0 --target-tags=web
Health checks to one service account's VMs | ... --rules=tcp:8080 --source-ranges=130.211.0.0/22,35.191.0.0/16 --target-service-accounts=SA_EMAIL
Record what a rule matches | gcloud compute firewall-rules update allow-web --enable-logging
N: Here are the commands in full. Read the first one as a sentence: on this network, for ingress, allow T-C-P four four three, from anywhere, to V-Ms tagged web. The second allows load balancer health checks to the V-Ms of one service account. Notice those two source ranges, as we come back to them. And the third turns on logging for a rule.

= dia | Targets | Tag, service account or secure tag
p4-tag-vs-sa
N: Now, how you choose a target matters. On the left, a network tag is a plain string, and anyone able to edit the V-M can add it. Adding web silently opens that V-M to the web rule. In the middle, a target service account can be changed only by someone who may attach that account, and only while the V-M is stopped. On the right, a secure tag needs an I-A-M role to attach its value. So ensure only the web tier's V-Ms receive this traffic, even if developers edit instances, points at service accounts or secure tags. Now read the note.
V: Network tags work only in V-P-C firewall rules. Firewall policies use secure tags, not network tags.

= table | Firewall policies | Hierarchical, global and regional
Policy | Attached to | Use
**Hierarchical** | Organization or folder | Guardrails for every VPC beneath: *"block this range everywhere"*
**Global network** | One VPC, all regions | Modern replacement for VPC rules: secure tags, FQDNs, geolocation, address groups
**Regional network** | One VPC in one region | Region-specific rules
> A fourth action: `goto_next` hands evaluation down. A new policy does nothing until **associated**.
N: The second kind of container is the firewall policy. A hierarchical policy attaches to the organization or a folder, and gives guardrails for every V-P-C beneath, such as block this range everywhere. A global network policy attaches to one V-P-C across all regions, and it is the modern replacement for V-P-C rules, with secure tags, domain names, geolocation and address groups. A regional network policy attaches to one V-P-C in one region. Policy rules add a fourth action, go to next, which hands evaluation down to the next level. And a new policy does nothing until it is associated.

= dia | Evaluation order | Top to bottom, stopping at the first allow or deny
p4-firewall-order
N: Evaluation runs left to right here, and it stops at the first allow or deny. One, the hierarchical policy at the organization. Two, hierarchical policies on folders, top down. Three, V-P-C firewall rules and the global network policy, whose relative order is configurable per network. Four, the regional network policy. And five, the implied rules: allow egress, deny ingress. So a rule at the organization wins over anything a project team writes, unless it says go to next.

= panel new | Cloud NGFW and secure tags | Resource-manager tags with a firewall purpose
**Secure tags** are tags created with the firewall purpose and bound to a VPC. Attach tag values to VMs or GKE node pools; policy rules select by those values.
Attaching needs `roles/resourcemanager.tagUser`, so **a developer cannot open a VM to a rule by editing it**.
**Tiers:** **Essentials** (stateful firewall, policies, secure tags) · **Standard** (FQDN, geolocation, threat intelligence) · **Enterprise** (intrusion prevention, TLS inspection)
N: New in the guide: secure tags. They are resource-manager tags created with the firewall purpose and bound to a V-P-C. You attach tag values to V-Ms or G-K-E node pools, and firewall policy rules select sources and targets by those values. Since attaching a value needs an I-A-M role, a developer cannot open a V-M to a rule simply by editing it. That is the property network tags lack. There are three tiers. Essentials is the foundational stateful firewall, with policies and secure tags. Standard adds domain name objects, geolocation and threat intelligence lists. Enterprise adds intrusion detection and prevention, with T-L-S inspection. To move an existing V-P-C's rules into a policy, use the migration tool, and rules using network tags need a mapping to secure tags first.

## 4.5 Shared VPC and VPC Network Peering

= table | Connecting networks | Three needs, three products
Need | Product | Deciding property
**One network, many projects**; a central team owns it | **Shared VPC** | Host + service projects, **one** network
**Two separate VPCs**, private, no gateways | **VPC Network Peering** | Native, full bandwidth, **non-transitive**
**Many VPCs**, hub-and-spoke, transitive | **Network Connectivity Center** | Spokes reach each other
N: Three needs, three products. One network used by many projects, where a central team owns subnets, routes and firewalls, and app teams keep their own projects: Shared V-P-C. Two separate V-P-Cs, private connectivity, no gateways: V-P-C Network Peering, native, full bandwidth and non-transitive. Many V-P-Cs and on-premises sites, in a hub and spoke, with transitivity: Network Connectivity Center.

= dia | Shared VPC | Host project and service projects
p4-shared-vpc
N: On the left, the host project owns the V-P-C: the network, subnets, routes and firewalls, run by a central team. On the right, service projects are attached, and create resources in the host's subnets. Team A's V-Ms live in the web subnet, but those V-Ms and their bills belong to team A's project. The network belongs to the host. It requires an organization. A service project attaches to one host, and a host cannot also be a service project.

= table sm | Shared VPC roles and commands | Two roles, at very different scopes
Role or task | Detail
**Shared VPC Admin** | `roles/compute.xpnAdmin`, at the org or a folder: enables hosts, attaches service projects
**Network User** | `roles/compute.networkUser` on the host, or on **individual subnets** for least privilege
Make the host | `gcloud compute shared-vpc enable HOST_PROJECT`
Attach a service project | `gcloud compute shared-vpc associated-projects add SVC --host-project=HOST`
One subnet only | `gcloud compute networks subnets add-iam-policy-binding web-euc2 --region=R --member=group:team-a@example.com --role=roles/compute.networkUser`
N: Two roles. The Shared V-P-C Admin, known as X-P-N admin, is granted at the organization or a folder. It enables hosts and attaches service projects. Network User lets service-project developers place resources in the subnets. It can be granted on the whole host project, or on individual subnets, which is the least-privilege answer.

= dia | VPC Network Peering | Non-transitive
p4-peering
N: Peering. A is peered with B, and B is peered with C. Can A reach C? Follow the red line.
V: Peering is non-transitive. If A peers with B, and B with C, A cannot reach C.
[pause: 0.8]
N: Nor can a peer use your V-P-N or Interconnect to reach your on-premises network, unless custom routes are exported and imported. Both sides must create the peering before it becomes active. The networks can be in different projects, or different organizations. Ranges must not overlap. Subnet routes are exchanged automatically, while custom routes need export and import. Firewall rules are never exchanged, so each side still controls its own ingress. Peering is also how private services access works for Cloud SQL and Memorystore, which is why those services inherit non-transitivity.

= panel tip | How to read the stem | When a stem forgives a weakness, it names the product that has it
*"Transitive routing is not required"* points straight at **peering**.
*"No gateways or tunnels in the path"* eliminates **VPN**.
*"A central network team must own the firewall rules"* is **Shared VPC**, not peering.
N: Here is a useful reading trick. When a stem forgives a weakness, it is naming the product that has it. Transitive routing is not required points straight at peering. No gateways or tunnels in the path eliminates V-P-N. A central network team must own the firewall rules is Shared V-P-C, not peering.

## 4.6 Hybrid connectivity: VPN, Interconnect, Cloud Router

= table sm | Hybrid options | Path, capacity, SLA
Product | Path | Capacity | SLA
**HA VPN** | IPsec over the internet | ~3 Gbps per tunnel (*verify*) | **99.99%** with 2 interfaces, 2 tunnels
Classic VPN | IPsec, one interface | Same | 99.9%; legacy
**Dedicated Interconnect** | Your circuits in a Google **colo** | 10 or 100 Gbps | 99.9 or 99.99%
**Partner Interconnect** | Via a provider | 50 Mbps to 50 Gbps | 99.9 or 99.99%
**Cross-Cloud Interconnect** | Circuits to AWS, Azure, OCI | 10 or 100 Gbps | 99.9 or 99.99%
Direct or Carrier Peering | To Google's edge | Varies | None; public services, **not your VPC**
N: The hybrid options. H-A V-P-N is IPsec over the internet, about three gigabits per tunnel, and you can add tunnels. It reaches ninety-nine point nine nine percent with two interfaces and two tunnels. Classic V-P-N is the legacy option at ninety-nine point nine. Dedicated Interconnect means your own circuits, in a Google colocation facility, at ten or one hundred gigabits. Partner Interconnect goes through a provider, from fifty megabits to fifty gigabits per attachment, when you cannot reach a colocation facility. Cross-Cloud Interconnect is a private link to another cloud. And direct or carrier peering reaches Google's public services, not your V-P-C, with no service level agreement.

= dia | Do the bandwidth sum first | Three stems, three answers
p4-hybrid-pick
N: Do the bandwidth sum first. Two gigabits, encrypted, next week: H-A V-P-N. Twenty gigabits sustained, in a facility where Google is present: Dedicated Interconnect. Five gigabits, with your data centre nowhere near a Google facility: Partner Interconnect. Now the red note.

[pause: 0.6]

= panel key | Cloud Router | The regional BGP speaker for your VPC
It learns on-premises prefixes over VPN or Interconnect, and advertises your subnets back.
**HA VPN requires it.** With the VPC's **dynamic routing mode set to global**, routes learned in one region are usable from all regions.
N: Cloud Router is the regional B-G-P speaker for your V-P-C. It learns on-premises prefixes, and it advertises your subnets back. H-A V-P-N requires it. And if on-premises routes are only reachable from one region, the fix is the V-P-C's dynamic routing mode. Set it to global, and routes learned in one region become usable from all regions.

= table | BGP in one page | The protocol Cloud Router speaks
Term | Meaning on Google Cloud
**BGP** | Border Gateway Protocol: routers **advertise** the prefixes they reach and **learn** the other side's
**ASN** | Each side's autonomous system number. Cloud Router needs a **private** one: `64512–65534` or `4200000000–4294967294`, different from on-premises
**BGP session** | One per tunnel or VLAN attachment, on **link-local** addresses from `169.254.0.0/16`
**Advertised routes** | Default: the subnets (per routing mode). **Custom**: add ranges, such as `199.36.153.8/30`
**MED / route priority** | **Lower is preferred**: different values make one tunnel active, one standby
N: What is B-G-P? Border Gateway Protocol is the routing protocol networks use to tell each other which address ranges they can reach. It is how internet providers exchange routes, and it is how Cloud Router and your on-premises router exchange them, over a V-P-N tunnel or an Interconnect attachment. Nobody types the other side's routes: each router advertises its prefixes, and the other learns them. Each side has an autonomous system number. Cloud Router needs a private one, from sixty-four thousand five hundred and twelve to sixty-five thousand five hundred and thirty-four, or the four billion range, and it must differ from the on-premises number. Each session runs on link-local addresses, one sixty-nine dot two five four. By default the router advertises your subnets, and a custom advertisement can add ranges, such as the private Google A-P-Is range. And each route carries a priority, sent as the multi-exit discriminator, where lower is preferred.

= dia | BGP | Two tunnels, two sessions, one router
p4-bgp
N: Here is an H-A V-P-N with B-G-P. The on-premises router, autonomous system sixty-five thousand and one, and Cloud Router, sixty-five thousand and ten. One session over each tunnel. What the router learns becomes dynamic routes in the V-P-C. Now the important part. When a tunnel fails, its routes are withdrawn, and traffic moves to the other tunnel by itself. That is why H-A V-P-N's ninety-nine point nine nine percent service level agreement requires dynamic routing, and why a new on-premises subnet appears in Google Cloud with nobody editing a route.
V: H-A V-P-N supports B-G-P only. Classic V-P-N is the one with static routes.

## 4.7 Private access to Google and to services

= table sm | Private access | Six needs, six mechanisms
Need | Mechanism

## 4.10 Network Service Tiers, Cloud CDN and Cloud Armor

= table | Network Service Tiers | Backbone or public internet

## 4.11 Seeing the network: flow logs, firewall logs, Connectivity Tests

= table sm | Network observability | Five tools

= panel watch | Easy to confuse | Flow logs versus firewall logs
**Flow logs** say *what traffic flowed*: sampled, per subnet.
**Firewall logs** say *which rule decided* a connection.
The **implied** deny-ingress rule cannot be logged. To log denied traffic, create an explicit low-priority deny rule with logging on.
`gcloud compute networks subnets update web-euc2 --region=R --enable-flow-logs`
N: Flow logs say what traffic flowed. Firewall logs say which rule decided a connection. And the implied deny ingress rule cannot be logged. On a firewall policy, too, you set enable logging on the rule, because flow logs sample and do not name the rule.

= list | More to recognise | Firewall, routing, connectivity, NAT

- **NCC with VPC spokes:** any-to-any among many VPCs. **HA VPN to AWS:** two connections, **four tunnels** for 99.99%
- **Cross-region internal Application LB** fails over internal traffic; a **serverless NEG per region** does it for Cloud Run
- Full GKE Pod range? Add a secondary range and new node pools with `--pod-ipv4-range`
N: A few more to recognise. An address group is a reusable list of I-P ranges for policy rules. Get effective firewalls lists every rule and policy that applies to one V-M. A policy-based route matches on source range and protocol, while static routes match destinations only. Network Connectivity Center with V-P-C spokes gives any-to-any connectivity among many V-P-Cs. H-A V-P-N to A-W-S uses two connections and four tunnels for the ninety-nine point nine nine percent topology. A cross-region internal Application load balancer fails internal traffic over between regions, and a global external one, with a serverless network endpoint group per region, does the same for Cloud Run. And a full G-K-E Pod range is extended by adding another secondary range and new node pools.

## Part 4 sample questions

= th | Part 4 · practice | Ten exam-style questions | Ask which way the traffic flows, who owns it, and what the stem forgives.
N: Ten questions. For each one, ask which way the traffic flows, who owns the network, and what the stem forgives.

= q | A subnet in `europe-central2` is nearly out of addresses, and new VMs for the same workload must land in that region. You want the least disruption. What should you do?
(A) Create a new VPC with a larger range and migrate
(B) Run `gcloud compute networks subnets expand-ip-range` with a shorter prefix
(C) Delete the subnet and recreate it larger
(D) Add a secondary range and place VMs on it
ans B
why A :: A new VPC is almost never the answer to "out of IPs".
why B :: Expansion needs no downtime, as long as the range does not overlap.
why C :: Needs an outage and a migration.
why D :: Secondary ranges are for alias IPs, such as GKE Pods.
C: The answer is B. The deciding clauses are the same workload, the same region, and least disruption. Expansion happens without downtime. A and C are heavy and disruptive. D misuses secondary ranges, which serve alias addresses like G-K-E Pods, not primary V-M interfaces.

= q | Developers can edit VM metadata and network tags. Security needs only the web tier to receive HTTPS, even if a developer edits an instance. Which firewall target should you use?
(A) A network tag `web` in a VPC firewall rule
(B) A target service account on the rule
(C) All instances in the network
(D) A source range of `0.0.0.0/0` with no target
ans B
why A :: Anyone able to edit the VM can add the tag.
why B :: Changing it needs permission to attach the account, with the VM stopped.
why C :: Opens every VM.
why D :: With no target, the rule applies to every instance.
C: The answer is B. Even if a developer edits an instance is the deciding clause. A network tag is only a string on the V-M, so a developer can add it. A target service account needs permission to attach, and the V-M has to be stopped. A secure tag in a firewall policy would also satisfy this, though it is not offered here. C and D open everything.

= q | You create a global **network firewall policy** and write a rule targeting the network tag `web`. It cannot be configured that way. Why, and what is the fix?
(A) Firewall policies use secure tags, so attach a secure tag value to the VMs
(B) Network tags only work if the policy is associated at the folder level
(C) The policy needs a higher priority number
(D) Cloud NGFW Enterprise is needed for tag targets
ans A
why A :: Policies select by secure tags, not network tags.
why B :: Association level does not change this.
why C :: Priority has nothing to do with target types.
why D :: Secure tags are available in Essentials.
C: The answer is A. The mapping runs one way only: network tags work only in V-P-C firewall rules, and firewall policies use secure tags. B and C change the wrong setting. D is a trap, since secure tags are part of the Essentials tier, with no extra charge.

= q | A central network team must own subnets and firewall rules, while four application teams keep their own projects and billing. What should you set up?
(A) VPC Network Peering between five VPCs
(B) Shared VPC with one host project and four service projects
(C) One project for everyone, with folders per team
(D) HA VPN tunnels between the teams' VPCs
ans B
why A :: Each VPC keeps its own firewalls, so no central ownership.
why B :: One network, centrally owned, with separate projects.
why C :: Loses separate billing and quota per team.
why D :: Tunnels add cost and complexity, with no central control.
C: The answer is B. A central team must own subnets and firewalls is the deciding clause, and keep their own projects is the second. Shared V-P-C gives exactly that. In peering, each side keeps its own firewall rules, so A fails. C removes the project boundary. D adds tunnels and solves nothing.

= q | VPC A is peered with VPC B, and VPC B is peered with VPC C. A VM in A cannot reach a VM in C. Routes and firewalls in B look correct. Why?
(A) Peering is non-transitive, so A and C need their own connection, or a hub
(B) A firewall rule in B is blocking the traffic
(C) Peered VPCs need the same project
(D) The peering needs Premium Tier
ans A
why A :: Peering is not transitive.
why B :: B is never in the path.
why C :: Peers can be in different projects and organizations.
why D :: Tiers apply to internet traffic, not peering.
C: The answer is A. Peering is non-transitive. To connect them, peer A with C directly, or use Network Connectivity Center. B is tempting, but B's firewall is not in the path at all. C and D are simply false.

= q | A company needs 5 Gbps to Google Cloud. Its data centre is far from any Google colocation facility, and traffic must not cross the public internet. What should it use?
(A) Dedicated Interconnect
(B) Partner Interconnect
(C) HA VPN
(D) Direct Peering
ans B
why A :: Needs your own circuits in a colocation facility.
why B :: A provider bridges the distance, up to 50 Gbps.
why C :: Runs over the public internet.
why D :: Reaches Google public services, not your VPC.
C: The answer is B. Three facts decide it: five gigabits, far from a facility, and not over the public internet. Dedicated needs you in a colocation facility. H-A V-P-N crosses the internet. And direct peering reaches Google's public services, not your V-P-C.

= q | Private VMs in a subnet need to read from Cloud Storage and BigQuery. They have no external IPs, and nothing else needs to be reached. What is the minimum configuration?
(A) Cloud NAT in the region
(B) Enable Private Google Access on the subnet
(C) A Dedicated Interconnect
(D) A public IP on one bastion VM, with a proxy
ans B
why A :: Works, but gives internet egress they do not need.
why B :: A per-subnet setting that reaches Google APIs only.
why C :: Hybrid connectivity to on-premises is unrelated.
why D :: Adds a public surface and a machine to run.
C: The answer is B. Nothing else needs to be reached is the deciding clause. Private Google Access is a per-subnet setting, and it reaches Google A-P-Is only. A would work, but it opens internet egress they do not need. C and D are unrelated or worse.

= q | On-premises servers must resolve names in a Cloud DNS **private zone**. They connect over HA VPN. What should you configure?
(A) A forwarding zone for the private domain
(B) A DNS inbound server policy on the VPC
(C) A public zone with the same names
(D) A peering zone on-premises
ans B
why A :: A forwarding zone sends queries from the Cloud to on-premises: the other direction.
why B :: Gives on-premises clients an address to query in the VPC.
why C :: Exposes private names on the internet.
why D :: Peering zones resolve between VPCs.
C: The answer is B. Direction decides the object. The query travels from on-premises into the Cloud, so that is an inbound server policy. A is the opposite direction, and it is the classic near miss. C publishes private names. D works between V-P-Cs.

= q | A game server uses UDP and must see each player's real source IP. Players connect to one region. Which load balancer fits?
(A) Global external Application Load Balancer
(B) External proxy Network Load Balancer
(C) External passthrough Network Load Balancer
(D) Internal Application Load Balancer
ans C
why A :: HTTP only, so no UDP.
why B :: A proxy hides the client IP, and this one carries TCP and SSL.
why C :: Carries UDP and preserves the client IP.
why D :: Internal and HTTP only.
C: The answer is C. Run the eliminations. U-D-P removes every Application load balancer, so A and D are out. Must see the source address removes every proxy, so B is out. Only passthrough is left.

= q | You created an external Application Load Balancer. Every backend shows unhealthy, but the application responds when you connect to a VM over its internal IP. What should you do first?
(A) Allow `35.191.0.0/16` and `130.211.0.0/22` to the serving port in a firewall rule
(B) Switch from Premium to Standard Tier
(C) Reserve a static IP for the load balancer
(D) Enable Cloud CDN on the backend service
ans A
why A :: Probes from those ranges are dropped by implied deny ingress.
why B :: The tier does not affect health checks.
why C :: The address does not affect backend health.
why D :: A cache does not make backends healthy.
C: The answer is A. All backends unhealthy right after creation, with a working application, is almost always the health check ranges. They arrive at the firewall as ingress, so without a rule, the implied deny drops them. The others change things that do not affect health checks.

## Part 4: frequently missed patterns

= th | Part 4 · more practice | Addresses, routing, DNS and load balancers | Ask which way the traffic flows, and which region it starts in.
N: 7 more questions, built on the patterns that candidates most often get wrong in this part. Answer each one before the reveal, and say which phrase in the stem decides it.

= q | Payment workers at Olmstead Retail run on VMs without external IPs in a managed instance group that recreates them often. They call a partner's API, and the partner will accept traffic only from two fixed public addresses it adds to an allow-list. What should you configure?
(A) Give each VM a static external IP address
(B) Cloud NAT with two static external IPs, assigned manually
(C) Cloud NAT with automatic IP allocation
(D) Private Google Access on the subnet
ans B
why A :: Static IPs per VM break as the group recreates VMs, and expose the VMs to inbound traffic.
why B :: Correct. Manual NAT IP assignment makes all of the subnet's egress leave from reserved addresses that never change, however often the VMs are recreated.
why C :: Automatic allocation can change or add addresses, which breaks an allow-list.
why D :: Private Google Access reaches Google APIs, not a partner's API.
C: The answer is B. Manual NAT IP assignment makes all of the subnet's egress leave from reserved addresses that never change, however often the VMs are recreated.

= q | Customers allow-list the IP address of your global external Application Load Balancer, which you will rebuild next month. The address must stay the same. What should you do?
(A) Reserve a regional static external IP address in us-central1
(B) Keep the ephemeral address by never deleting the forwarding rule
(C) Reserve a global static external IP for the new forwarding rule
(D) Use the load balancer's DNS name instead of an IP
ans C
why A :: A regional address cannot be used by a global forwarding rule.
why B :: The rebuild will delete the forwarding rule, releasing an ephemeral address.
why C :: Correct. Global load balancers need global addresses. A reserved static address stays in the project and can be attached to a new forwarding rule.
why D :: The customers allow-list an IP address, not a DNS name.
C: The answer is C. Global load balancers need global addresses. A reserved static address stays in the project and can be attached to a new forwarding rule.

= q | Services in a Cloud DNS private zone api.internal.example must be resolvable by on-premises clients connected over Cloud Interconnect. On-premises DNS can forward a domain to any IP address you give it. What should you configure in Google Cloud?
(A) A forwarding zone for api.internal.example pointing at the on-premises resolvers
(B) Make the private zone public so on-premises clients can resolve it
(C) A DNS peering zone in the on-premises network
(D) An inbound DNS server policy, forwarded to from on-premises DNS
ans D
why A :: A forwarding zone sends queries from Cloud to on-premises — the other direction.
why B :: Publishing internal names on the internet is the wrong fix.
why C :: Peering zones are between VPC networks in Cloud DNS, not on-premises.
why D :: Correct. An inbound server policy creates resolver entry points in the VPC's subnets that on-premises DNS can forward to, which answer from the private zones visible to the VPC.
C: The answer is D. An inbound server policy creates resolver entry points in the VPC's subnets that on-premises DNS can forward to, which answer from the private zones visible to the VPC.

= q | An internal HTTP service runs in us-east1 and us-west1. Internal clients should use one internal address, and if the us-east1 backends fail, traffic should go to us-west1 automatically. What load balancer fits?
(A) A regional internal Application Load Balancer in us-east1
(B) A global external Application Load Balancer
(C) An internal passthrough Network Load Balancer
(D) A cross-region internal Application Load Balancer
ans D
why A :: A regional load balancer's backends are all in one region.
why B :: An external load balancer exposes the service to the internet.
why C :: The passthrough Network Load Balancer is regional and Layer 4.
why D :: Correct. The cross-region internal Application Load Balancer has backends in several regions and fails over between them for internal clients.
C: The answer is D. The cross-region internal Application Load Balancer has backends in several regions and fails over between them for internal clients.

= q | You create a custom-mode VPC with one subnet and no firewall rules, then two VMs in it, each with an external IP address. What does the firewall allow between the VMs and the internet?
(A) Outbound connections only; no inbound, not even between the two VMs
(B) All traffic between the two VMs is allowed; only internet ingress is blocked
(C) No traffic is possible at all until an egress rule is created
(D) SSH and ICMP from anywhere are allowed, as in the default network
ans A
why A :: Correct. Without explicit rules, the implied rules apply: allow all egress, deny all ingress. Internal traffic is ingress to the receiving VM, so it is denied too.
why B :: Internal traffic is not special; it needs an ingress allow rule like any other.
why C :: Egress is allowed by the implied rule, so no egress rule is needed.
why D :: SSH, ICMP and internal allows are pre-populated rules of the default network, not implied rules of new VPCs.
C: The answer is A. Without explicit rules, the implied rules apply: allow all egress, deny all ingress. Internal traffic is ingress to the receiving VM, so it is denied too.

= q | An HA VPN and Cloud Router in europe-west4 learn the on-premises prefixes over BGP. VMs in europe-west4 reach on-premises, but VMs in us-central1 on the same VPC do not. What should you change?
(A) Set the VPC network's dynamic routing mode to global
(B) Create a second HA VPN and Cloud Router in us-central1 only
(C) Add static routes for the on-premises prefixes in us-central1
(D) Peer the VPC with itself across regions
ans A
why A :: Correct. In regional mode a Cloud Router programs learned routes only in its own region; global dynamic routing makes them available to every region of the VPC.
why B :: A second gateway would work but adds cost and management when a setting solves it.
why C :: Static routes duplicate what BGP already provides and must be maintained by hand.
why D :: A VPC cannot peer with itself.
C: The answer is A. In regional mode a Cloud Router programs learned routes only in its own region; global dynamic routing makes them available to every region of the VPC.

= q | A VPC-native GKE cluster cannot add nodes because its Pod secondary range is exhausted, and the range cannot be expanded because neighbouring ranges are in use. What should you do?
(A) Recreate the cluster with a larger Pod range
(B) Switch the cluster to routes-based networking
(C) Lower the maximum Pods per node on the existing node pool in place
(D) Add a secondary range for Pods, used by new node pools
ans D
why A :: Recreating the cluster is disruptive and unnecessary.
why B :: A cluster cannot be converted from VPC-native to routes-based.
why C :: Max Pods per node cannot be changed on an existing node pool.
why D :: Correct. GKE supports additional, discontiguous Pod ranges. New node pools can take their Pod IPs from a new secondary range, so the cluster keeps growing without being recreated.
C: The answer is D. GKE supports additional, discontiguous Pod ranges. New node pools can take their Pod IPs from a new secondary range, so the cluster keeps growing without being recreated.
