## 5.4 Disks: Persistent Disk, Hyperdisk and Local SSD

= table sm | Disk types | Network block storage, and one that is not
Type | Nature | Notes
**pd-balanced** | SSD-backed | Good default
**pd-ssd** | Higher IOPS per GB | Databases on older series
**pd-standard** | HDD-backed | Cheapest, sequential throughput
**Hyperdisk Balanced, Throughput, Extreme** | **IOPS and throughput provisioned independently of size** | Newest series (C4, N4) support **only** Hyperdisk (*verify*)
**Hyperdisk ML** | Read-only, **many VMs at once** | Serving model weights to a fleet
**Local SSD** | Physically attached, 375 GB partitions | **Fastest, ephemeral**
N: Disk types. Balanced persistent disk is the good default. S-S-D persistent disk gives higher I-O operations per gigabyte, and standard persistent disk is the cheapest, backed by hard drives. New in the guide: Hyperdisk, in Balanced, Throughput and Extreme, where performance is provisioned independently of size. Remember that the newest machine series, such as C4 and N4, support only Hyperdisk. Hyperdisk ML is read-only and attaches to many V-Ms at once, for serving model weights. And Local S-S-D is physically attached, the fastest of all, and ephemeral.

= dia | What survives what | Four kinds of durability
p5-disk-survive
N: Now compare what each one survives, from left to right. Local S-S-D survives a reboot or live migration, but its data is lost when the V-M stops or is deleted. A zonal disk lives in one zone, and attaches only to V-Ms in that zone. A regional disk, or Hyperdisk Balanced High Availability, is synchronously replicated across two zones, so it survives a zone failure, and you force-attach it to a standby V-M. A snapshot is backup, which you can restore anywhere, but it is a point in time.
V: Regional disks are high availability. Snapshots are backup.
[pause: 0.6]
N: So survive a zone failure with no data loss, for a single-V-M database, is a regional disk, and not a snapshot schedule.

= cmd | Disk rules and commands | Up, never down
Task | Command
Grow a disk, never shrink | gcloud compute disks resize data-2 --zone=Z --size=1TB
Attach an existing disk | gcloud compute instances attach-disk web-1 --disk=data-2 --zone=Z
Regional disk, two zones | gcloud compute disks create db-ha --region=R --replica-zones=R-a,R-b --type=pd-balanced
>! Local SSD plus a durability requirement is always wrong. Grow the file system inside the guest after a resize.
N: Four rules of thumb. Disks can be resized up, never down, while attached, and you then grow the file system inside the guest. Local S-S-D plus a durability requirement is always wrong, as it is for scratch and caches. Regional disks are high availability, and snapshots are backup. And zonal disks attach only to V-Ms in their zone, so to move one, snapshot it and create a disk elsewhere.

## 5.5 Connecting to instances: SSH keys, OS Login, IAP

= table | Two ways SSH is authorised | Metadata keys, or IAM
Method | Access is | Revoke by | Choose when
**Metadata SSH keys** | Public keys in project or instance metadata | Removing the key | Small, informal set-ups
**OS Login** | Linux accounts **tied to Google identities**, granted by an **IAM role** | Removing the role, or suspending the user | **The recommended answer** for teams
N: Two ways Linux S-S-H access is authorized. Metadata S-S-H keys are public keys placed in project-wide or instance metadata. You revoke by removing the key from metadata, which suits small set-ups. OS Login ties Linux accounts to Google identities, so access is an I-A-M role. You revoke by removing the role, or by suspending the user. That is the recommended answer for teams.

N: OS Login is enabled with the metadata key enable O-S login, on a project or instance, or enforced org-wide with the require O-S login constraint. Then access is pure I-A-M. And users outside your organization need the external user role on the organization. O-S Login is Linux only, as Windows uses R-D-P, with a password from gcloud compute reset windows password.

## 5.7 Snapshots, images and machine images

= dia | Four artefacts | What each one captures
p5-artefacts
V: Snapshot: one disk's data. Image: one bootable disk. Machine image: the whole V-M. Template: a recipe.
[pause: 0.8]
N: Walk through them. A snapshot captures one disk's data, incrementally, and you use it to back up or clone that disk, in any zone or region. A custom image captures one disk as a bootable image, and boots new V-Ms from a golden state. It is what an instance template references. A machine image captures all of a V-M's disks plus its configuration: machine type, metadata, labels, tags, network and service account. Use it to clone, back up or move a whole V-M. An instance template is only a specification, with no data, which tells a managed instance group what to create.

= list | Snapshots | The details the exam uses
- **Incremental:** the first is full; deleting one never breaks the others
- Stored multi-regionally or regionally, so a disk can be created anywhere
- **Snapshot schedules:** resource policies on disks, with retention. A cron job is the distractor
- **Archive snapshots** cost less to store, more to restore
- **Instant snapshots:** fast, in-place rollback, **not** a backup, since they live with the disk
- For application consistency, quiesce the application, or use **VSS** on Windows
N: Snapshot details. They are incremental. The first is full, later ones store changed blocks, and deleting one never breaks the others. Snapshot schedules are resource policies attached to disks, with retention. They are the managed answer to, back up these disks nightly and keep fourteen days. Archive snapshots cost less to store and more to restore. Instant snapshots are fast, in-place copies for rollback, and not a backup, since they live with the disk. And for application consistency, quiesce the application, or use V-S-S on Windows.

= list | Images | Families, deprecation, sharing, golden images
- **Image families** point at the newest non-deprecated image
- Build `hardened-v7`, add it to family `hardened`: every template using the family picks it up
- **Deprecation states:** `DEPRECATED` (warn), `OBSOLETE` (no new use), `DELETED`
- **Share** across projects: `roles/compute.imageUser` on the image project
- **Golden image:** *"boot already hardened, no configuration at start-up"*. A startup script can fail
N: Images. An image family points at the newest non-deprecated image. So build hardened v-seven, add it to the family hardened, and every template using the family picks it up. Deprecation states are deprecated, obsolete and deleted. Share images across projects by granting Compute Image User on the image project. And the golden image pattern: every V-M must boot already hardened, with no configuration step at start-up. You bake a custom image, because a startup script is configuration at boot, and it can fail.

= th | Instance templates | A template is <em>immutable</em> | To change what a group creates, make a new template, and roll it out. Templates are global or regional.
V: An instance template is immutable. To change what a group creates, make a new template, and roll it out.
[pause: 0.6]

= table | Managed or unmanaged | Almost always managed
Property | Managed (MIG) | Unmanaged
Instances | Identical, **from a template** | Any VMs you add by hand
Autoscaling, autohealing, rolling updates | **Yes** | No
Use | Almost everything | Load-balancing a mixed legacy set
Zonal or regional | **Regional MIGs** spread across zones, three by default | Not applicable
N: A managed instance group, or MIG, holds identical V-Ms from a template, with autoscaling, autohealing and rolling updates. An unmanaged group holds any V-Ms you add by hand, with none of those features. It only suits load-balancing a mixed legacy set. A zonal MIG keeps all its V-Ms in one zone. A regional MIG spreads them across zones, three by default, and survives a zone outage. That is the answer to must stay up if a zone fails.

= dia | Four features | Each one solves a different problem
p5-mig-features
N: Four MIG features, and each solves a different problem. Autohealing, with a health check on the MIG: the V-M is up, but the application is broken, and the MIG recreates it. Autoscaling: not enough or too much capacity, so it changes the count. Rolling updates: rolling a new template out without an outage. Regional distribution: surviving a zone failure. And the red note.
V: A load balancer's health check only stops sending traffic. The MIG's autohealing check recreates the V-M.
[pause: 0.6]
N: The broken V-M would otherwise keep running forever. Give autohealing an initial delay long enough for boot, or it will kill instances in a loop.

= table | Autoscaling | Signals and controls
Signal | Example
**CPU utilisation** | Target 60% average
**Load-balancing serving capacity** | Utilisation or RPS per instance behind an HTTP(S) LB
**Cloud Monitoring metric** | Per-instance or per-group, e.g. Pub/Sub backlog
**Schedules** | Scale up at 08:00 on weekdays
> Also: min and max replicas, **initialisation period**, **scale-in controls**, **predictive** autoscaling.
N: Autoscaling signals. C-P-U utilization, such as a target of sixty percent. Load balancing serving capacity. A Cloud Monitoring metric, such as Pub/Sub backlog per instance. And schedules, such as scale up at eight on weekdays. Other controls: minimum and maximum replicas, the initialization period, which is how long a new V-M is ignored while it warms up, scale-in controls, which limit how fast it shrinks, and predictive autoscaling for C-P-U patterns.

= dia | Updating a group | A canary, then a full rollout with no capacity loss
p5-rolling
N: Now a rollout, step by step. One, you start an update, with a canary version at twenty percent. Two, the MIG creates twenty percent of the group from template version two. Three, those V-Ms pass health checks, and receive traffic. You watch the errors. Four, highlighted, you start the full update, with max surge three and max unavailable zero, so capacity never drops. Five, the MIG surges new V-Ms first. Six, it deletes old V-Ms as new ones pass. And rollback is simply another start update, back to version one.

= cmd sm | Group commands | Autoscale, heal, canary, roll
Task | Command
Autoscale on CPU | gcloud compute instance-groups managed set-autoscaling web-mig --region=R --min-num-replicas=3 --max-num-replicas=12 --target-cpu-utilization=0.6
Autohealing | gcloud compute instance-groups managed update web-mig --region=R --health-check=hc-http --initial-delay=300
Canary: 20% | ... rolling-action start-update web-mig --region=R --version=template=web-v1 --canary-version=template=web-v2,target-size=20%
Full, no capacity loss | ... rolling-action start-update web-mig --region=R --version=template=web-v2 --max-surge=3 --max-unavailable=0
Restart or recreate every VM | ... rolling-action restart web-mig · ... rolling-action replace web-mig
N: On screen are the commands. Set autoscaling, with minimum, maximum and target. Update with a health check, and an initial delay. Then rolling action start update, with the two version forms. And rolling action restart or replace.

= table | Update knobs | What each flag does
Knob | Effect
`--max-surge` | Extra instances above target during the update
`--max-unavailable` | How many may be down at once; 0 = never below target
`--type=proactive` or `opportunistic` | Replace now, or only when recreated anyway
`--replacement-method=substitute` or `recreate` | New names, or keep names (stateful MIGs)
**Stateful MIGs** | Preserve per-instance disks, metadata, IPs across recreation
N: The knobs. Max surge creates extra instances above target, keeping capacity. Max unavailable says how many may be down at once. Type proactive replaces now, and opportunistic replaces only when instances are recreated anyway. Replacement method substitute gives new names, and recreate keeps names, needed for stateful MIGs. And stateful MIGs preserve per-instance disks, metadata and addresses across recreation, for workloads such as databases that need stable identity.

## 5.9 GPUs and TPUs

= dia new | GPUs or TPUs | The choice is about the workload
p5-gpu-tpu
N: New in the guide: identify whether to use G-P-Us or T-P-Us, and attach them. On the left, G-P-Us from NVIDIA are general-purpose parallel processors. They run anything using CUDA: PyTorch, TensorFlow, custom kernels. They are strong for broad model variety, inference, graphics, rendering and video. On the right, T-P-Us are Google's own chips, built for large tensor operations. They use JAX, PyTorch with X-L-A, or TensorFlow. They are strong at large-scale training and serving, at the lowest cost at scale. T-P-Us come as chips, hosts and slices. And when the stem gives no framework constraint and the workload is general, G-P-U is the safer answer.

= panel tip | Stem language | Which accelerator
*"Rendering"*, *"video transcoding"*, *"custom CUDA kernels"*, *"a few GPUs for inference"*: **GPU**.
*"Train a very large transformer in JAX as cheaply as possible at scale"*: **TPU**.
*"Very large training across thousands of chips"*: a **multi-host TPU slice**.
N: The language. Rendering, video transcoding, custom CUDA kernels, a few G-P-Us for inference: G-P-U. Train a very large transformer in JAX, as cheaply as possible at scale: T-P-U. Very large training across thousands of chips: a multi-host T-P-U slice, joined by the inter-chip interconnect.

= list new | Attaching GPUs | The hard constraints
- **A2, A3, A4, G2:** GPUs built into the machine type; choose `a2-highgpu-1g`, not `--accelerator`
- **N1** takes attached GPUs: `--accelerator=type=nvidia-tesla-t4,count=1`. E2 and C3 take none
- **`--maintenance-policy=TERMINATE`**: GPU VMs cannot live-migrate
- **Drivers:** a GPU-ready image (Deep Learning VM), or install them; GKE can do it for you
- **Quota:** per region **and** all regions; request both
- **Availability:** only certain **zones**; check `accelerator-types list`
N: Attaching G-P-Us has hard constraints. Accelerator-optimised series have G-P-Us built into the machine type, so you choose the machine type, and not an accelerator flag. N1 V-Ms take attached G-P-Us with the accelerator flag, and E2 and C3 take none. Maintenance policy must be terminate. For drivers, use a G-P-U-ready image, such as a Deep Learning V-M, or install them, and G-K-E can install them for you. Quota exists per region and across all regions, and you may need both. And G-P-U and T-P-U types exist only in certain zones, so if the create call fails in a zone, check accelerator types list. Spot pricing applies too. Graphics desktops use NVIDIA G-P-Us with R-T-X Virtual Workstation images.

= list | More to recognise | Beyond the big four
- **Batch** runs arrays of tasks on VMs it creates and deletes
- **VMware Engine** moves vSphere estates unchanged. **Oracle Database@Google Cloud** runs Exadata
- **Future reservation** holds capacity: quota is permission, a commitment is a discount, neither is capacity
- **Dynamic Workload Scheduler flex-start** gets a set of GPUs together, without preemption during the run
- Regional MIG **target distribution shape `ANY`** places VMs where a zone has capacity
- **Hyperdisk Storage Pools** share capacity and performance across disks
N: A few more to recognise. Batch runs arrays of tasks on V-Ms it creates and deletes. VMware Engine moves vSphere estates unchanged. A future reservation holds capacity for a known date. And note this sentence: quota is permission, a commitment is a discount, and neither is capacity. Dynamic Workload Scheduler flex start gets a set of G-P-Us together, when capacity appears. A regional MIG's target distribution shape, any, places V-Ms wherever a zone has capacity. And Hyperdisk Storage Pools share capacity and performance across many disks.

## Part 5 sample questions

= th | Part 5 · practice | Ten exam-style questions | Name the failure each option survives, and what the stem forgives.
N: Ten questions. For each one, ask what failure or cost the stem is really about.

= q | An overnight rendering job can restart from checkpoints, and cost is the main concern. What should you use?
(A) Sole-tenant nodes
(B) Spot VMs in a managed instance group
(C) A three-year resource-based commitment
(D) Standard VMs with autoscaling
ans B
why A :: The most expensive option, for isolation needs.
why B :: Interruptible and restartable is exactly what Spot suits.
why C :: A commitment suits steady 24×7 work, not nightly runs.
why D :: Works, but at full price.
C: The answer is B. Restart from checkpoints and cost are the deciding clauses. Spot gives a large discount in exchange for possible preemption, and the instance group recreates V-Ms as capacity returns. A is for isolation. C suits a steady footprint. D works, but costs more than it needs to.

= q | A VM creation fails when you request a GPU with the default settings: *"Instances with guest accelerators do not support live migration."* What is the fix?
(A) Set `--maintenance-policy=TERMINATE`
(B) Request a GPU quota increase
(C) Use a regional disk
(D) Enable `--can-ip-forward`
ans A
why A :: GPU VMs cannot live-migrate, so they must terminate on maintenance.
why B :: The message is not about quota.
why C :: Disks have nothing to do with this.
why D :: IP forwarding is for appliances.
C: The answer is A. The error message tells you the reason, and you must know the flag. G-P-U V-Ms cannot live-migrate, and migrate is the default, so you set terminate. B would apply to a different error. C and D are unrelated.

= q | A single-VM database must lose no committed data if a zone fails, and recover quickly on a standby VM in another zone. What should you use?
(A) A daily snapshot schedule
(B) A regional Persistent Disk, force-attached to the standby
(C) Local SSD with a RAID array
(D) A custom image rebuilt nightly
ans B
why A :: Loses everything since the last snapshot.
why B :: Synchronous across two zones, so no committed data is lost.
why C :: Local SSD is ephemeral, and it is lost with the VM.
why D :: An image is a boot source, not live data.
C: The answer is B. No committed data loss rules out point-in-time copies. A regional disk replicates synchronously across two zones. A loses what was written since the last snapshot. C fails the rule that Local S-S-D plus durability is always wrong. D is not live data.

= q | You must let an engineer SSH to private VMs, with no bastion and no external IPs, using per-user authorization. Which **two** steps are required? Choose two.
(A) Grant `roles/iap.tunnelResourceAccessor` to the engineer
(B) Allow `35.235.240.0/20` to port 22 in a firewall rule
(C) Reserve a static external IP for each VM
(D) Add the engineer's key to project-wide metadata
(E) Enable Private Google Access on the subnet
ans A, B
why A :: Authorizes the tunnel for that user.
why B :: IAP connects from this range.
why C :: Contradicts "no external IPs".
why D :: Gives access to every VM in the project.
why E :: For reaching Google APIs, not for inbound SSH.
C: The answers are A and B. Tunnelling through Identity-Aware Proxy needs a role for the user, and a firewall rule for the proxy's range. C contradicts the stem. D is the project-wide key trap. E is a common confusion, since Private Google Access is outbound to Google A-P-Is, and has no effect on inbound S-S-H.

= q | An application occasionally hangs while its VM stays running. Instances sit in a managed instance group behind a load balancer. Users are not affected, but capacity silently shrinks over time. What should you add?
(A) An autohealing health check on the MIG, with a suitable initial delay
(B) A larger CPU target for the autoscaler
(C) A second load-balancer health check
(D) A shutdown script
ans A
why A :: Recreates VMs that fail the application check.
why B :: Does not repair a broken VM.
why C :: Only stops traffic, which is already happening.
why D :: Runs only when a VM is shutting down.
C: The answer is A. The clue is that users are not affected. The load balancer's health check already stops traffic to a hung V-M, but the V-M keeps running forever. Only the MIG's autohealing health check recreates it. Set the initial delay long enough for boot, or it will kill instances in a loop.

= q | You must roll a new template to a regional MIG with **no reduction in serving capacity**. What should you use?
(A) `rolling-action start-update` with `--max-surge=3 --max-unavailable=0`
(B) `rolling-action start-update` with `--max-surge=0 --max-unavailable=3`
(C) Edit the existing instance template in place
(D) Delete the MIG and create a new one from the new template
ans A
why A :: New VMs first, and never below target.
why B :: Takes VMs down before replacements exist.
why C :: Templates are immutable.
why D :: Causes an outage.
C: The answer is A. Zero unavailable means never below target, and a surge provides the room to do it. B reverses the settings. C is impossible, since a template is immutable. D is an outage.

= q | You need to recreate a VM in another zone: all three of its disks, its machine type, metadata, tags and service account, with the fewest steps. What should you use?
(A) Three snapshots
(B) A custom image of the boot disk
(C) A machine image
(D) An instance template
ans C
why A :: Moves data, but loses configuration.
why B :: Contains only one disk.
why C :: All disks plus configuration.
why D :: A recipe with no data.
C: The answer is C. All disks plus configuration is precisely a machine image. A loses the configuration. B has one disk. D has no data at all. Remember the sentence: snapshot, one disk's data. Image, one bootable disk. Machine image, the whole V-M. Template, a recipe.

= q | Your security team requires every VM to boot already hardened, with no configuration step at start-up. New VMs come from a MIG. What should you do?
(A) Add a startup script that applies the hardening
(B) Build a custom image in an image family, and reference the family in a new template
(C) Use an OS policy to apply the settings after boot
(D) Take a snapshot of the hardened disk, and attach it after boot
ans B
why A :: Configuration at boot, which is what the stem rules out.
why B :: The golden-image pattern.
why C :: Enforces after boot, not at it.
why D :: Attaching a data disk does not change the boot state.
C: The answer is B. No configuration step at start-up is the clause. That rules out startup scripts and post-boot enforcement, which are A and C. A custom image in a family is the golden image pattern. Since templates are immutable, you reference it in a new template.

= q | A research team will train a very large transformer written in JAX, and wants the lowest cost at scale. Another team renders video with custom CUDA kernels. Which accelerators fit, in order?
(A) GPUs for both
(B) TPUs for the training, GPUs for the rendering
(C) TPUs for both
(D) GPUs for the training, TPUs for the rendering
ans B
why A :: Works, but misses the cost at scale for JAX training.
why B :: Each workload matched to its accelerator.
why C :: TPUs do not run CUDA, or render graphics.
why D :: The reverse of the right mapping.
C: The answer is B. Very large J-A-X training at the lowest cost at scale points to T-P-Us. Custom CUDA kernels and rendering point to G-P-Us, because CUDA is NVIDIA's platform, and T-P-Us never render graphics. So C and D are impossible, and A misses the cost clause.

= q | You must patch 400 Linux VMs every Sunday, limit how many reboot at once, and report which are non-compliant. What should you use?
(A) A cron job on each VM
(B) A VM Manager patch deployment with a rollout and a disruption budget
(C) New images, with a rolling update every Sunday
(D) Cloud Scheduler calling a shell script over SSH
ans B
why A :: The assembled distractor, and no compliance view.
why B :: Scheduled, controlled, and with compliance reporting.
why C :: Heavy, and it applies only to MIGs.
why D :: Assembled, and with no compliance reporting.
C: The answer is B. The three requirements, on a schedule, limit concurrency, and report compliance, map exactly onto a patch deployment. A and D are the assembled answers, and we prefer managed over assembled. C is sometimes valid for immutable groups, but the stem does not say these V-Ms are in a group.

## Part 5: frequently missed patterns

= th | Part 5 · more practice | VMs, groups and accelerators | Look for the word that says what must survive.
N: 5 more questions, built on the patterns that candidates most often get wrong in this part. Answer each one before the reveal, and say which phrase in the stem decides it.

= q | On Rydal Games' matchmaking servers, the process sometimes hangs while the VM stays running, so the VM keeps receiving traffic. The servers run in a regional managed instance group on a custom VPC that has only rules for its own subnets. Hung VMs must be recreated automatically. Which two actions should you take? (Choose two.)
(A) Set the VMs' availability policy to restart them automatically after a failure
(B) Create an uptime check on the load balancer's address that alerts the on-call team
(C) Allow ingress from 35.191.0.0/16 and 130.211.0.0/22 on the matchmaking port
(D) Install the Ops Agent on each VM so that process metrics reach Cloud Monitoring
(E) Create a health check for the port, set as the group's autohealing policy
ans C, E
why A :: Automatic restart reacts to a VM crash or host event; the VM here is still running.
why B :: An uptime check alerts people; it doesn't recreate anything in the group.
why C :: Correct. Without ingress from the probe ranges, the health checks fail on every VM.
why D :: The Ops Agent collects metrics and logs; it has no part in autohealing.
why E :: Correct. An autohealing policy with an application health check detects the hung process, not just a stopped VM.
C: The answer is C and E. Autohealing recreates a VM when the group's health check reports it unhealthy. The probes come from Google's health-check ranges, which a custom VPC with no matching rule would block, making every VM look unhealthy.

= q | After an engineer edits the network configuration inside a Linux VM's guest OS, the VM has no network connectivity at all: SSH fails, including through IAP. You need a console prompt on the VM to repair the configuration. What should you do?
(A) Enable OS Login and grant yourself the OS Login Admin role
(B) Connect through Identity-Aware Proxy TCP forwarding
(C) Add a new SSH key to the instance metadata
(D) Enable the interactive serial console and connect to it
ans D
why A :: OS Login changes who may log in over SSH; SSH still needs the network that is broken.
why B :: IAP tunnels to the VM's network interface, which is down inside the guest.
why C :: A new key still needs a working network path for SSH.
why D :: Correct. The serial console doesn't depend on the guest's network, so it gives a login prompt to fix the configuration.
C: The answer is D. The interactive serial console is reached through Compute Engine, not the guest's network stack, so it works when the VM's own networking is broken.

= q | A standalone n2-standard-4 VM needs to become n2-standard-8, keeping its boot disk, internal IP address and metadata. What is the procedure?
(A) Stop the VM, change its machine type, then start it
(B) Change the machine type while it runs; vCPUs are hot-added
(C) Create a snapshot and build a new VM of the larger type from it
(D) Attach a second n2-standard-4 to the VM as an accelerator
ans A
why A :: Correct. Stop, set the new machine type, and start; the instance keeps its disks and configuration.
why B :: vCPUs and memory can't be hot-added; the VM must be stopped.
why C :: A new VM works, but it is a different instance with new settings to recreate, which is more work than needed.
why D :: Machine types aren't accelerators and can't be attached to a VM.
C: The answer is A. Compute Engine changes a VM's machine type only when the VM is stopped. The disks, addresses and metadata stay with the instance.

= q | A research team runs long simulations on Spot VMs with state on the boot disk. When a VM is pre-empted, they want to restart it later from where the disk left off, not rebuild it. How should the VMs be created?
(A) Spot VMs whose termination action is DELETE
(B) Spot VMs whose termination action is STOP
(C) Preemptible VMs with automatic restart turned on
(D) Standard VMs carrying a spot=true label
ans B
why A :: DELETE removes the VM, and its boot disk too by default.
why B :: Correct. A Spot VM's termination action decides what pre-emption does: STOP keeps the VM and its disks so you can start it again later; DELETE removes the VM.
why C :: Pre-emptible and Spot VMs cannot use automatic restart.
why D :: Labels do not change the provisioning model or price.
C: The answer is B. A Spot VM's termination action decides what pre-emption does: STOP keeps the VM and its disks so you can start it again later; DELETE removes the VM.

= q | A research lab will pre-train a very large JAX model for weeks across thousands of accelerator chips. Its code has no custom CUDA kernels, and cost per training step is the main criterion. What should it plan to use?
(A) Thousands of single-GPU N1 VMs in a managed instance group
(B) Spot C3 VMs with many vCPUs each
(C) Cloud Run jobs with GPUs attached
(D) A multi-host Cloud TPU slice
ans D
why A :: Loosely connected single-GPU VMs scale poorly for synchronous training at this size.
why B :: CPUs are far too slow for this workload.
why C :: Cloud Run jobs are not built for weeks-long, tightly coupled training across thousands of chips.
why D :: Correct. TPU slices are built for large-scale training. Frameworks such as JAX use the inter-chip interconnect to scale across hosts efficiently, typically with strong price-performance.
C: The answer is D. TPU slices are built for large-scale training. Frameworks such as JAX use the inter-chip interconnect to scale across hosts efficiently, typically with strong price-performance.
