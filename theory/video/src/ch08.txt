## 8.1 Infrastructure as code: the model

= table | Declarative or scripted | Why the exam prefers declarative
Property | Declarative IaC | A script of `gcloud`
You write | The **desired end state** | The **steps**
Re-running | **Idempotent** | Fails or duplicates
Preview | **Plan, diff before apply** | None
Drift | **Detected** on the next plan | Invisible
Review | A pull request on a readable diff | Review of imperative code
N: Infrastructure as code describes infrastructure in version-controlled files, and lets a tool make reality match them. The exam prefers it over console clicks and shell scripts for anything repeatable, and it prefers declarative tools. With a declarative tool, you write the desired end state, and with a script, you write the steps. Re-running a declarative tool is idempotent, changing only what differs, while a script fails or duplicates. You get a plan before you apply. Drift is detected on the next plan. And reviewers see a readable diff.

When an option offers Terraform or Infrastructure Manager against any of these, Terraform wins.
N: Three wrong answers to spot. Deployment Manager is deprecated, so never choose it for new work. Console export gives a one-time copy, not a maintained definition. And a shell script is repeatable, but not declarative. When an option offers Terraform or Infrastructure Manager against any of these, Terraform wins.

## 8.2 Terraform on Google Cloud

= table | Terraform vocabulary | Five words
Concept | Meaning
**Provider** | The plug-in that talks to an API: `google`, `google-beta`
**Resource**, **data source** | Something Terraform manages; something it only reads
**Module** | A reusable package of resources, with inputs and outputs
**State** | The mapping from code to real resource IDs
**Plan**, **apply** | Compute the diff; execute it
N: Terraform vocabulary. A provider is the plug-in that talks to an A-P-I. A resource is something Terraform manages, and a data source is something it only reads. A module is a reusable package, with inputs and outputs. State is Terraform's record of what it manages, the mapping from code to real resource I-Ds. And plan computes the diff, while apply executes it.

= dia | The recommended loop | And the exam's items are mostly about state
p8-terraform-loop
N: Follow the boxes. Code lives in git, and is reviewed by pull request. Terraform plan computes the diff, which you attach to the review. Terraform apply runs from a pipeline, as a dedicated deploy account, reached by impersonation or federation. And state lives remotely.
V: Store state remotely, in a Cloud Storage backend, with locking.
[pause: 0.6]
N: Then two applies cannot run at once. Local state on laptops is the classic failure: two engineers, two truths.

= list | State rules | The heart of Terraform
- State contains **secrets and resource details**: restrict the bucket, enable **versioning**, never commit it
- **One state per environment** limits the blast radius
- Existing resources come in with **`import`** blocks or `terraform import`, not delete and recreate
- **Pin** provider and module versions: `version = "~> 7.0"`
- `terraform init` → `terraform plan -out=tfplan` → `terraform apply tfplan`
N: More rules about state. It contains secrets and resource details, so restrict the bucket, enable versioning to recover a corrupted state, and never commit it to git. One state per environment limits the blast radius of a mistake. Resources made by hand are brought under management with import blocks or terraform import, and not by deleting and recreating them. Pin provider and module versions, so a plan today means the same tomorrow. And the loop is init, plan, apply.

= panel key | Infrastructure Manager | Terraform, without owning the runner
Google's managed service that **runs Terraform for you**: it stores state, runs plans (*previews*) and applies (*revisions*) as a service account, and records history.
N: Infrastructure Manager is Google's managed service that runs Terraform for you. It stores state, runs plans, which it calls previews, and applies, which it calls revisions, as a service account, and it records history. So it is Terraform, without owning the runner or the state bucket.

## 8.3 Blueprints and Kubernetes-native tools

= table sm | Blueprints and tools | Which tool for which request
Tool | What it is | Choose it when

N: Beyond raw Terraform. Cloud Foundation Toolkit is Google-maintained Terraform modules and blueprints. Config Connector is a Kubernetes add-on that manages Google Cloud resources as Kubernetes custom resources. Config Controller is a hosted version. And Helm is the package manager for Kubernetes, with charts, values and releases.

= dia | Easy to confuse | When does reconciliation happen?
p8-tf-vs-kcc
N: These are easily confused. Terraform and Config Connector are both declarative. Terraform reconciles when you run it. Config Connector reconciles continuously, inside a cluster, so a console change is reverted automatically, and it suits teams already working in Kubernetes YAML. Helm deploys applications into Kubernetes, and it does not create the cluster or cloud resources.

## 8.4 Making changes the recommended way

= list | Six habits | The recommended way to change infrastructure
- **Version control**: changes by pull request, with the `plan` attached
- **Apply from a pipeline**, as a **dedicated deploy service account**, by impersonation or federation, never a key
- **Least privilege per stage**; separate states per environment
- **No manual console changes**: the next `plan` shows the **drift**
- **Policy as code**: org policies, plus `gcloud beta terraform vet`
- **Promote the same code** through environments, with different variables
N: Six habits make up the recommended way. Everything in version control, with changes by pull request and the plan attached for review. Apply from a pipeline, not a laptop, running as a dedicated deploy service account, reached by impersonation or Workload Identity Federation, never a key. Least privilege per stage, so the networking pipeline cannot touch I-A-M on the organization. No manual console changes in managed environments. If one happens, the next plan shows the drift, and you revert it in code, or adopt it into code. Policy as code, with organization policies as guardrails, and plan validation before apply. And promote the same code from development to staging to production, with different variables, and not three copies.

= list new | Agent Runtime | A managed runtime for AI agents
- For agents built with the **Agent Development Kit (ADK)**, LangChain, LangGraph
- Provides **scaling, sessions, memory, identity, tracing, logging**
- Deploy from the SDK or console: package, **deploy to a region**, give it a **service identity** with only the roles its tools need

N: Agent Runtime is a managed runtime for A-I agents, built with the Agent Development Kit, LangChain, LangGraph and other frameworks. You deploy the agent, and it provides scaling, sessions, memory, identity, tracing and logging. It is the compute answer for, host our agent without building the serving infrastructure. The alternative is packaging the agent yourself on Cloud Run or G-K-E. To deploy, you package the agent, deploy it to a region, and give it a service identity with only the roles its tools need. The deployment names its requirements, and only those packages are installed, so module not found after deploy means a missing requirement. It needs a staging bucket, kept in the agent's project. And you release a new version by updating the existing resource, so callers keep its name. Agent Identity gives each agent its own principal, and deleting the agent does not remove bindings to that principal.

## Part 8 sample questions

= th | Part 8 · practice | Seven exam-style questions | Which tool fits, and what stays true because an AI wrote it.
N: Seven questions, on which tool fits, and on using it safely.

= q | Two engineers run Terraform from their laptops and keep overwriting each other's changes. What is the best fix?
(A) Store state in a Cloud Storage backend, with locking and versioning
(B) Commit the state file to git
(C) Take turns, using a chat channel
(D) Switch to Deployment Manager
ans A
why A :: Shared state, and locking stops concurrent applies.
why B :: Exposes secrets, and git does not lock.
why C :: A process that relies on people remembering.
why D :: Deprecated, and it does not address the problem.
C: The answer is A. The classic failure is two engineers with two truths. A shared backend gives one truth, locking prevents concurrent applies, and versioning recovers a corrupted state. B puts secrets in git. C is not a control. D is deprecated.

= q | A storage bucket was created by hand last year. It must now be managed by Terraform, without any downtime or data loss. What should you do?
(A) Delete the bucket, and let Terraform recreate it
(B) Write the resource in code, and use an `import` block or `terraform import`
(C) Copy the data to a new bucket managed by Terraform, then delete the old one
(D) Use the console's export once, and then ignore drift
ans B
why A :: Destroys the data.
why B :: Adopts the existing resource into state.
why C :: Works, but it is unnecessary and disruptive.
why D :: A one-time copy, not a maintained definition.
C: The answer is B. Import brings an existing resource into state, without touching it. A loses data. C moves everything when it does not need to, and bucket names are globally unique, so the new name would change too. D does not manage the resource.

= q | Application teams already use Kubernetes YAML and GitOps. They want to manage their Cloud SQL instances and buckets the same way, with console changes reverted automatically. What should they use?
(A) Helm
(B) Terraform run from CI
(C) Config Connector
(D) Deployment Manager

why A :: Deploys applications into Kubernetes, not cloud resources.
why B :: Reconciles only when it runs.
why C :: Cloud resources as Kubernetes objects, continuously reconciled.
why D :: Deprecated.
C: The answer is C. Kubernetes YAML and automatic reverting are the two deciding clauses. Config Connector reconciles continuously, in a cluster. Terraform reconciles only when you run it. Helm packages applications. And D is deprecated.
