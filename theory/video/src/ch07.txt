## 7.1 Choosing a storage product

= table sm | Access model first | The product follows from the access model
Access model | Product | Pick it when the stem says
**Objects** over HTTPS | **Cloud Storage** | "files", "backups", "data lake", "static website", "archive"
**Block** device for one VM | **Persistent Disk, Hyperdisk** | "boot disk", "database on a VM"
**Shared NFS** for many VMs or Pods | **Filestore** | "shared file system", "ReadWriteMany in GKE"
**NAS: NFS and SMB** | **NetApp Volumes** | "SMB", "Windows file shares", "migrate our NetApp"
**Parallel file system** | **Managed Lustre** | "AI training data loading", "HPC scratch"
Ephemeral local scratch | **Local SSD** | "temporary", "cache", "scratch"
N: Start with the access model the application needs, and the product follows. Objects over H-T-T-P-S, of any size and number: Cloud Storage. A block device for one V-M: Persistent Disk or Hyperdisk. A shared P-O-S-I-X file system, N-F-S, for many V-Ms or Pods: Filestore. Enterprise network storage with N-F-S and S-M-B: NetApp Volumes. A parallel file system with very high throughput for thousands of clients: Managed Lustre. And ephemeral, ultra-fast local scratch: Local S-S-D.

= dia new | The file-storage family | Three products, three deciding words
p7-file-family
N: New in the guide: the file storage family. Filestore is managed N-F-S, in tiers from basic H-D-D to zonal, regional and enterprise. Regional survives a zone. NetApp Volumes is NetApp's storage run by Google, with N-F-S and S-M-B, Active Directory integration, volume snapshots, backups and replication. It is the answer whenever Windows, S-M-B or NetApp appears. Managed Lustre is a fully managed parallel file system for A-I and H-P-C, where aggregate throughput to many clients matters more than anything else. None of them is object storage, and none is the answer to cheap archive.

## 7.2 Cloud Storage: buckets, locations, classes

= table sm | Cloud Storage facts | Buckets and objects
Concept | Fact
**Bucket names** | **Globally unique**, immutable; **location** also fixed at creation
**Objects** | Immutable: a change writes a new object or *generation*; no partial updates
Consistency | **Strong** read-after-write and list consistency
**Location type** | **Region** · **dual-region** (optional **turbo replication**, within 15 min) · **multi-region** (`US`, `EU`, `ASIA`)
Storage class | A bucket **default**, overridable **per object**
N: Bucket names are globally unique and immutable, and a bucket's location is also fixed at creation. Objects are immutable, so a change writes a new object or generation, with no partial updates. Consistency is strong, for read after write and for lists. Locations are a region, a dual region, or a multi-region. A dual region is a predefined pair, or a configurable pair you choose within one continent, with optional turbo replication within fifteen minutes. And the storage class is a bucket default, overridable per object.

= dia | The four classes | Memorise 0, 30, 90, 365
p7-classes
V: Memorise zero, thirty, ninety, three hundred sixty-five.
[pause: 0.6]
N: Those are the minimum storage durations. Standard has no minimum, for frequently accessed data. Nearline is thirty days, for about once a month. Coldline is ninety days, for about once a quarter. Archive is three hundred and sixty-five days, for once a year or less. As you move right, the storage price falls, and the retrieval fee rises. Deleting, overwriting or moving an object before its minimum is billed as if it had stayed the full minimum. And now the red note.
V: All four classes have the same millisecond latency to the first byte.
[pause: 0.8]
N: There is no thaw, no restore step, and no waiting. That is a different cloud's archive model. So a stem that says read once a year, but must be available immediately when requested, is still Archive. The immediately clause decides nothing.

> **Autoclass** moves each object by its access, with no retrieval or early-deletion charges: *"patterns unknown or changing"*.
N: Autoclass moves each object between classes automatically, based on its access pattern, with no retrieval or early-deletion charges. It is the answer to, access patterns are unknown or change. It replaces lifecycle class transitions on that bucket. The commands all begin with gcloud storage: buckets create with location and class, cp and rsync for copying, and objects update to change one object's class.

## 7.3 Lifecycle, versioning, soft delete and retention

= table sm | Six protections | What each feature does
Feature | Does | Typical stem
**Lifecycle rules** | **Delete** or **SetStorageClass** by age, versions, class | "Nearline after 30 days, delete after a year"
**Versioning** | Keeps **noncurrent versions** | "recover a file someone overwrote"
**Soft delete** | Deleted objects restorable, **7 days default**, up to 90 | "undo an accidental delete from yesterday"
**Retention policy** | **No delete or overwrite** until the age | "keep every record for 7 years"
**Bucket Lock** | **Locks** the policy **permanently** | "WORM", "immutable, even from admins"
**Holds** | Per-object temporary or event-based holds | "legal hold on these files"
N: Six features. Lifecycle rules delete objects, or set a colder class, by age, by the number of newer versions, by current class and more. Versioning keeps noncurrent versions when an object is overwritten or deleted. Soft delete keeps deleted objects restorable for a window, seven days by default on new buckets. A retention policy means objects cannot be deleted or overwritten until they reach an age. Bucket Lock locks the retention policy permanently, so it can be lengthened, but never shortened or removed. And object holds put a hold on individual objects, for a legal hold.

= dia | Accidents or intent | Different protections for different threats
p7-protect
N: Compare them by threat. Versioning and soft delete protect against accidents, since someone with permission can still remove versions. A locked retention policy protects against intent. Nobody, including an Owner, can delete the object early, and nobody can unlock the policy. One more fact: lifecycle rules only move objects to colder classes, and never warm them up, and changes can take up to twenty-four hours to act.

= cmd sm | Protection commands | Lifecycle, versioning, retention, holds
Task | Command
Lifecycle rules (a JSON file) | gcloud storage buckets update gs://B --lifecycle-file=lifecycle.json
Versioning | gcloud storage buckets update gs://B --versioning
Soft-delete window | gcloud storage buckets update gs://B --soft-delete-duration=30d
Retention, then lock (irreversible) | ... --retention-period=7y · ... --lock-retention-period
Hold one object | gcloud storage objects update gs://B/contract.pdf --temporary-hold
N: Most are options on gcloud storage buckets update. A lifecycle file is JSON, with actions and conditions such as age and number of newer versions. Lock retention period is irreversible, so be sure before you run it.

## 7.4 Securing objects

= table sm | Securing objects | Access mechanisms
Mechanism | Use
**Uniform bucket-level access** | **IAM only**, no ACLs: recommended. Reversible for 90 days, then permanent
Fine-grained | IAM plus per-object **ACLs**: legacy only
**Public access prevention** | Blocks `allUsers`, `allAuthenticatedUsers`; also by org policy
**Signed URL** | **Time-limited** access to one object, with **no Google identity**; V4 lasts at most 7 days
Signed policy document | Browser **form uploads**, with constraints
HMAC keys | S3-compatible tools
N: Securing objects. Uniform bucket-level access means I-A-M only, with no object access control lists, and it is the recommended setting. It is reversible for ninety days, then permanent. Fine-grained access adds per-object access control lists, for legacy needs only. Public access prevention blocks all users and all authenticated users. A signed U-R-L gives time-limited access to one object, for someone with no Google identity, for download or upload, and a version four U-R-L lasts at most seven days. A signed policy document is for browser form uploads with constraints. And HMAC keys serve S3 compatible tools.

= table | Storage roles | The ladder
Role | Grants
`storage.objectViewer` | Read and list objects
`storage.objectCreator` | Create objects, **not** read, overwrite or delete
`storage.objectUser` | Read, create, update, delete objects
`storage.objectAdmin` | Full control of **objects**, not bucket settings
`storage.admin` | Full control of buckets **and** objects
> `gcloud storage sign-url gs://B/report.pdf --duration=2h --impersonate-service-account=SA_EMAIL`
N: The role ladder. Object Viewer reads and lists. Object Creator creates, and cannot read, overwrite or delete. Object User reads, creates, updates and deletes. Object Admin has full control of objects, but not bucket settings. Storage Admin controls buckets as well. And look at the command. You can make a signed U-R-L with no key file, by impersonating a service account.

= panel tip | Stem language | Three storage access stems
*"A partner with no Google account must download one file this week"*: **signed URL**.
*"A drop box where uploaders must not read each other's files"*: **`objectCreator`**.
*"Manage objects but never change the bucket's settings"*: **`objectAdmin`**, not `admin`.
N: Three stems. A partner with no Google account must download one file this week: a signed U-R-L. A drop box where uploaders must not read each other's files: Object Creator. Manage objects, but never change the bucket's settings: Object Admin, and not Storage Admin.

## 7.5 Estimating storage cost

= table sm | What you pay for | The bill, per product
Product | You pay for | Levers
**Cloud Storage** | GB-months by class · **operations** · **retrieval** · early deletion · egress | Class, lifecycle, Autoclass
**PD, Hyperdisk** | **Provisioned** size; provisioned IOPS and throughput | Right-size; delete unattached disks
**Cloud SQL, AlloyDB** | vCPU, memory, storage; **HA roughly doubles** | HA only where needed
**BigQuery** | **Storage** (long-term after 90 days at half price) · **compute**: per TiB, or slots | Partition, cluster, fewer columns
**Spanner, Bigtable** | Nodes or PUs · storage · replication | Autoscaling
N: What you pay for. Cloud Storage bills gigabyte-months by class and location, operations, where writes and lists cost more than reads, retrieval on Nearline and colder, early deletion, and egress. Disks bill provisioned size, not used size. Cloud SQL and AlloyDB bill the instance, and high availability roughly doubles it. BigQuery bills storage, with long-term storage at about half price after ninety days unmodified, and compute, which is on-demand per tebibyte scanned, or capacity slots. Spanner and Bigtable bill compute capacity, storage and replication.

N: An important trap.

N: The bytes scanned are the columns read, across the partitions touched. So select fewer columns, filter on the partition column, and use clustering. A dry run tells you the bytes a query would scan, for free. And maximum bytes billed makes an expensive query fail, instead of running.

## 7.6 Choosing a database

= dia | Choosing a database | Seven products, and what points at each
p7-db-pick
N: Seven products. Walk down the list. Managed relational, one primary for writes, is Cloud SQL, with MySQL, Postgres or S-Q-L Server. Postgres, much faster, or transactions and analytics on the same data, is AlloyDB. Global relational, scaling writes, with strong consistency across regions, is Spanner. Time series, internet of things, hundreds of thousands of writes per second, key lookups, is Bigtable. Documents for a mobile or web app, with real-time sync, is Firestore. Analytics and S-Q-L over huge datasets is BigQuery. And cache, session store or leaderboard is Memorystore.

= table | Four eliminations | They decide most database items
# | Elimination
1 | Cloud SQL and AlloyDB **cannot scale writes horizontally**: beyond one primary, or across continents, is **Spanner**
2 | BigQuery is **not** a low-latency point-lookup or OLTP store
3 | Bigtable has **no joins, no multi-row transactions, no relational secondary indexes**
4 | Memorystore is a **cache**, never the system of record
N: Four eliminations decide most database items. One: Cloud SQL and AlloyDB cannot scale writes horizontally. So write throughput beyond one primary, or relational data spanning continents with strong consistency, is Spanner. Two: BigQuery is not a low-latency point lookup or transaction store. Three: Bigtable has no joins, no multi-row transactions, and no secondary indexes in the relational sense, so its design is row-key design. Four: Memorystore is a cache, and never the system of record.

## 7.7 Cloud SQL and AlloyDB

= table sm | Cloud SQL | The facts the exam uses
Topic | Fact
Editions | **Enterprise**, **Enterprise Plus** (higher SLA, data cache, near-zero-downtime maintenance)
**High availability** | A **regional** instance: synchronous **standby in another zone**. **Standby serves no reads**
**Read replicas** | **Asynchronous**, for **read scaling**; a cross-region replica can be **promoted**
**Backups** | **Automated** daily and **on-demand**; restoring **to an instance overwrites it**
**PITR** | Needs **binary logs** or **WAL archiving** **beforehand**; **clones to a new instance**
Connecting | **Auth Proxy**, connectors · **private IP** · IAM database authentication
N: Cloud SQL. Editions are Enterprise and Enterprise Plus. High availability is a regional instance, with a synchronous standby in another zone, and automatic failover. The standby serves no reads. Read replicas are asynchronous copies for scaling reads, in the same region or another, and a cross-region replica can be promoted for disaster recovery. Backups are automated daily, and on demand, and restoring to an instance overwrites it. Point-in-time recovery needs binary logging or write-ahead log archiving enabled beforehand, and it clones to a new instance. To connect, use the Cloud SQL Auth Proxy or connectors, private I-P, and I-A-M database authentication. Storage can grow automatically, but it cannot shrink.

= dia | Three different jobs | HA, replica and point-in-time recovery
p7-ha-replica-backup
V: High availability is not read capacity, and a replica is not a backup.
[pause: 0.6]
N: On the left, the high availability standby exists only to take over from a failed zone. In the middle, a read replica serves reads, but it replicates a destructive delete within seconds, so it cannot undo one. On the right, point-in-time recovery undoes a bad statement.

= dia | A bad DELETE at 14:05 | Lose the least data
p7-pitr
N: Follow the story. Message one, at five past two, a bad delete runs. Two, it is replicated to the read replica within seconds, so the replica is damaged too. Three, you run gcloud sql instances clone, with point in time at four minutes past two. Four, Cloud SQL builds a new instance as of that moment. The damaged original stays untouched for comparison. And five, you verify and then repoint the application. That is why this story is point-in-time recovery to a new instance, and not restoring a replica.

= cmd sm | Cloud SQL commands | Create, replicate, clone, promote
Task | Command
HA, PITR, private IP only | gcloud sql instances create orders --database-version=POSTGRES_16 --region=R --availability-type=REGIONAL --enable-point-in-time-recovery --no-assign-ip --network=vpc-prod
Read replica, another region | gcloud sql instances create orders-replica --master-instance-name=orders --region=R2
Restore to a moment, as new | gcloud sql instances clone orders orders-restored --point-in-time='2026-09-20T14:04:00Z'
Make the replica the primary | gcloud sql instances promote-replica orders-replica
Connect; export | gcloud sql connect orders --user=postgres · gcloud sql export sql orders gs://B/orders.sql.gz --database=shop
N: Read the first command as a checklist: availability type regional, for high availability. Enable point in time recovery. No assign I-P, with a network, for private only. Then the replica uses master instance name. Clone takes a point in time. And promote replica makes the replica a standalone primary.

= panel key | AlloyDB for PostgreSQL | Primary, read pools, columnar engine
A **cluster** holds a **primary** (HA by default across zones) and optional **read pool** instances.
The **columnar engine** accelerates analytics on live transactional data. **Continuous backup** restores to any point in its window (14 days default, *verify*).
**Cross-region secondary clusters** provide DR. Connects like Cloud SQL. *AlloyDB Omni* runs the same engine anywhere.
N: AlloyDB. A cluster holds a primary instance, highly available by default across zones, and optional read pool instances that scale reads. Its columnar engine accelerates analytical queries on live transactional data. Continuous backup allows restore to any point in its window. Cross-region secondary clusters provide disaster recovery. It connects like Cloud SQL. And AlloyDB Omni runs the same engine anywhere.

## 7.8 Spanner, Bigtable and Firestore

= list | Spanner | Horizontally scalable, strongly consistent relational
- **Configuration:** **regional** (99.99%), **dual-region** or **multi-region** (99.999%)
- **Capacity:** nodes or **processing units**; 1 node = 1,000 PU; from 100 PU; managed **autoscaling**
- **GoogleSQL** or **PostgreSQL** dialect; ACID across rows, tables, regions; **interleaved tables**
- **Hotspots:** an increasing primary key sends inserts to one split: use UUIDv4, bit-reversed sequences, a hashed prefix
- **Backups** and **PITR** within version retention, up to 7 days
N: Spanner. An instance has a configuration: regional at four nines, or dual-region or multi-region at five nines. Compute capacity is in nodes or processing units, where one node is a thousand processing units, and small instances start at one hundred. It has Google S-Q-L or a Postgres dialect, with A-C-I-D transactions across rows, tables and regions. The classic trap is hotspots. A monotonically increasing primary key, such as a timestamp or sequence, sends all inserts to one split. So use a U-U-I-D version four, bit-reversed sequences, or a hashed prefix.

= list | Bigtable | Row-key design is everything
- **Instance:** one or more **clusters**, one per zone; nodes scale throughput linearly
- **App profiles:** **single-cluster routing** (read-your-writes) or **multi-cluster** (failover, **eventual** consistency)
- Queries are by key or key range. Avoid keys starting with a timestamp or sequential ID
- Use `device#reverse_timestamp` shapes; keep related data adjacent
- **Backups** restore into a new table. Data access: **`cbt`**
N: Bigtable. An instance has one or more clusters, one per zone, with nodes that scale throughput linearly. Several clusters give replication. App profiles route traffic: single-cluster routing gives strong read your writes, and multi-cluster routing gives automatic failover, with eventual consistency between clusters. Row-key design is everything, since queries are by key or key range. Avoid keys that start with a timestamp or sequential I-D, as those create hotspots. Use a device, then a reverse timestamp, shape. Data access is with cbt, or client libraries.

= list | Firestore | Serverless documents
- **Native mode** (real-time listeners, offline SDKs) or **Datastore mode** (server workloads)
- **MongoDB compatibility:** standard drivers on serverless Firestore
- The **location is permanent**; a project can hold several **named databases**
- **Composite indexes** must be created for multi-field queries; **TTL policies** delete expired documents
- **PITR** (7 days), **scheduled backups**, export and import to Cloud Storage
N: Firestore. Native mode has documents in collections, real-time listeners, and offline mobile and web S-D-Ks. Datastore mode serves server workloads using the Datastore A-P-I. Firestore with MongoDB compatibility accepts standard Mongo drivers, so it answers, move a Mongo app to a serverless database with minimal code change. The location is permanent. Single-field indexes are automatic, and composite indexes must be created for multi-field queries. Recovery has point-in-time recovery for seven days when enabled, scheduled backups which restore into a new database, and export and import.

= cmd | Spanner | Which configurations exist, and where the replicas are
Task | Command
Every configuration available to the project | gcloud spanner instance-configs list
Replicas, their types and the default leader of one | gcloud spanner instance-configs describe eur5
> Dual-region configurations exist only for some country pairs. **List them** before designing around one.
N: Spanner instance configurations decide where replicas live: regional, dual-region or multi-region. Which ones exist for your project is a list, not a guess: gee-cloud spanner instance configs list. And describe on one of them shows each replica, its type, its region, and the default leader. Dual-region configurations exist only for some country pairs within a geography, so check before you design around one.

## 7.9 BigQuery

= table sm | BigQuery concepts | Hierarchy, partitions, pricing, recovery
Concept | Fact
Hierarchy | Project → **dataset** (a fixed **location**) → tables, views, materialized views
**Partitioning** | By ingestion time, a date column, or integer range; expiration drops old data
**Clustering** | Sorts within partitions by up to four columns
**Compute** | **On-demand** (per TiB) or **capacity** (editions: slots, reservations)
**Time travel** | Up to **7 days** (configurable 2–7), then **7 days of fail-safe**

N: BigQuery. The hierarchy is project, then dataset, which has a fixed location, then tables and views. Time travel lets you query or restore a table as of up to seven days ago, followed by seven days of fail-safe. And access takes two grants. Data viewer on the data, and job user on the project that runs the query.

## 7.11 Loading and moving data

= dia | Do the arithmetic first | Volume divided by bandwidth gives days
p7-transfer
V: One gigabit per second moves about ten terabytes per day. One hundred megabits moves about one.
[pause: 0.6]
N: Do the arithmetic before comparing tools. Volume divided by usable bandwidth gives days. If that is not acceptable, use Transfer Appliance, where you ship a device, load it on site, and send it back. If it is acceptable, ask where the data is. Another cloud, U-R-L lists or another bucket: Storage Transfer Service. On-premises file systems: Storage Transfer Service with agents. Small, one-off and scripted: gcloud storage cp or rsync. Into BigQuery on a recurring basis: BigQuery Data Transfer Service. Five hundred terabytes over one hundred megabits is about five hundred days, so only the appliance is left.

= table sm | Moving data | The tools, and when each is right
Tool | Right when
**`gcloud storage cp, rsync`** | Small or scripted
**Storage Transfer Service** | Large or **recurring**, from other clouds, URL lists, on-premises, between buckets
**Transfer Appliance** | Hundreds of TB, a **thin or busy link**, or a deadline
**`bq load`** | Batch loads **from Cloud Storage**: free
**External tables, BigLake** | **Query in place**
**BigQuery Data Transfer Service** | **Scheduled** loads from SaaS, GCS, S3
**Storage Write API**, Pub/Sub, Dataflow | **Streaming** into BigQuery
**Datastream** · **Database Migration Service** | Change data capture · migration into Cloud SQL or AlloyDB
N: In more detail. Storage Transfer Service handles large or recurring transfers, with scheduling, retries, integrity checks and bandwidth limits. bq load runs batch loads from Cloud Storage, in C-S-V, JSON, Avro, Parquet or O-R-C, and batch loading is free. External tables and BigLake query in place, without loading. The Storage Write A-P-I, Pub/Sub BigQuery subscriptions and Dataflow stream into BigQuery. Datastream does change data capture from MySQL, Postgres and Oracle. And Database Migration Service migrates databases into Cloud SQL or AlloyDB.

= cmd | Loading a file into a table | Append by default; replace on request
Task | Command
Replace a table from a CSV with a header row | bq load --replace --source_format=CSV --skip_leading_rows=1 sales.daily gs://kestrel-drop/daily.csv
Replace one day of a partitioned table | bq load --replace --source_format=CSV --skip_leading_rows=1 'sales.daily$20261108' gs://kestrel-drop/2026-11-08.csv
> A load job **appends** unless told otherwise. An **external table** queries the file where it is; `gcloud storage cp` never loads a table.
N: Loading a file into an existing table. A load job appends by default. Dash dash replace empties the table first, in the same job, so readers never see it half loaded. Skip leading rows equals one drops a C-S-V header. Point the load at one partition, with the dollar sign and the date, and only that day is replaced. An external table, by contrast, queries the file in place without loading it. And copying a file with gee-cloud storage never puts it in a table.

## 7.12 Messaging and pipelines: Pub/Sub, Managed Kafka, Dataflow

= table sm | Pub/Sub | Topics, subscriptions, delivery
Concept | Fact
**Delivery types** | **Pull**, **push** to HTTPS with OIDC, or **export** to **BigQuery** or **Cloud Storage**
Acknowledgement | At-least-once; **ack deadline** 10 s default, up to 600 s; **exactly-once** for pull
Retention | Unacked messages **7 days** default, up to 31
Failure | Retry policy; **dead-letter topic** after N attempts
Ordering, replay | **Ordering keys**; **snapshots** and **seek**
N: Pub/Sub. A topic is where publishers send messages. A subscription gets every message. Delivery is pull, push to an H-T-T-P-S endpoint with O-I-D-C authentication, or export straight into BigQuery or Cloud Storage. It is at least once by default, with an acknowledgement deadline of ten seconds by default, up to six hundred. Exactly once is available for pull. Unacknowledged messages are kept seven days by default. A dead-letter topic takes messages after N delivery attempts. Ordering keys preserve order per key. And snapshots and seek let you replay.

= dia new | Configuring CMEK | The service agent needs the key

= table | Three rules of CMEK | Each is a favourite distractor
Rule | Detail
**1 The service agent needs the key** | The Google-managed account needs `cryptoKeyEncrypterDecrypter`, not you

N: Three rules, and each is a favourite distractor. One, the service agent needs the key. Two, locations must match. = q | Compliance documents are read about once a year, must be kept for ten years, and must be readable immediately when requested. Which storage class minimizes cost?

= q | A regulator requires records to be immutable for seven years, even from project owners, and the policy must not be removable. What should you configure?

(B) Soft delete with a 90-day window
(C) A retention policy with Bucket Lock
(D) An IAM deny policy on `storage.objects.delete`

why A :: Someone with permission can still remove versions.
why B :: The window is too short, and it does not prevent deletion.
why C :: Locked retention cannot be shortened or removed by anyone.
why D :: An administrator could remove the policy.

D is tempting, since deny binds Owners, but a deny policy can be changed by someone with the right role. A locked retention policy cannot be removed by anyone.

= q | Your analytics team's on-demand BigQuery bill is too high. Queries use `SELECT *` over a table with years of data, filtered by date. Which **two** changes reduce the bytes billed? Choose two.
